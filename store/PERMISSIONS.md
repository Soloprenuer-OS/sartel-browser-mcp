# Permission justifications

One field per permission in the Chrome Web Store "Privacy practices" tab. Each block below is
verbatim paste-ready. They are written to be checkable against the source, because the source is
public — do not inflate them.

The framing that ties all of them together, and the answer to "why does one extension need all of
this": the extension has no features of its own. It is a remote-control surface. Every permission
here exists because some tool in the local MCP server's 41-tool surface calls the corresponding
Chrome API, on the user's explicit instruction, in the user's own browser.

---

## `debugger`

This is the one that decides the review. It is written as a mechanism, not a pitch.

```
Sartel operates the user's browser on their behalf, so its clicks and keystrokes have to be real
ones. chrome.debugger is the only API available to an extension that can produce trusted input
events — events with isTrusted=true, generated by the browser's own input pipeline rather than
synthesized in page script.

This is not a nicety. Events dispatched from content scripts (element.click(), new MouseEvent,
setting .value and firing 'input') are rejected or silently ignored by a large share of modern web
UI: React's synthetic event layer and controlled inputs, custom elements and shadow-DOM form
controls, rich text editors, drag handles, native <select> and date pickers, and any control that
checks event.isTrusted. Without trusted events an automation extension can navigate and read, but
cannot reliably fill in a form — which is the user's whole reason for installing this.

Concretely, the extension attaches the debugger to the specific tab it is acting on and sends only
these CDP commands:

  Input.dispatchMouseEvent   click, double-click, right-click, hover, scroll, drag
  Input.dispatchKeyEvent     typing, Enter/Tab/arrow keys, modifiers
  Input.insertText           text entry into focused fields
  DOM.getDocument, DOM.querySelector, DOM.focus   resolving the target element
  DOM.setFileInputFiles      user-initiated file upload (the only way to set a file input)
  Page.captureScreenshot     screenshots, including full-page beyond the viewport
  Page.handleJavaScriptDialog  answering native alert/confirm/prompt dialogs, which otherwise
                             block the tab forever with no other API able to dismiss them
  Runtime.evaluate           evaluating an expression in the page, for the user's own scripted
                             steps and for reading state after an action
  Runtime.enable / consoleAPICalled   collecting console output, so the agent can see page errors
  Network.enable / getResponseBody    reading a response the user asked the agent to fetch

That is the complete list. The debugger is attached per tab, only while the agent is acting on that
tab, and detached afterwards. Chrome shows its own "Sartel is debugging this browser" banner the
entire time it is attached, so the user always sees when this permission is in use.

What this permission is NOT used for here: it is not used for remote debugging, it does not open
or expose a debugging port, and it does not connect to any remote endpoint. The extension's only
network connection of any kind is a WebSocket to 127.0.0.1 on the user's own machine. No data
obtained through the debugger — page content, screenshots, console output, network bodies —
leaves the user's computer via this extension.

The source is public and MIT licensed, so every claim above is verifiable:
https://github.com/Soloprenuer-OS/sartel-browser-mcp
```

## Host permissions — `<all_urls>`

```
The user tells their agent which site to work on, and it can be any site: their own web app on
localhost, an internal admin tool, a documentation site, a supplier's ordering portal. The
extension cannot know that set in advance and has no list of supported sites, so there is no
narrower host pattern that would leave it functional.

Access is used only on the tab the agent is currently acting on, in response to an instruction the
user has given. The extension does not run any content script at document_idle, does not observe
browsing the user does themselves, and builds no history or profile. Nothing read from any host is
transmitted off the machine — the only connection is to 127.0.0.1.
```

---

## `scripting`

```
Injects the code that carries out DOM-level work on the tab the agent is acting on: locating an
element by text or CSS selector, reading page content and structure, scrolling an element into
view, dismissing cookie or newsletter overlays that block the flow, and rendering the in-page
overlay used to ask the user a question and wait for their answer. Injection happens on demand,
per action, into the tab the user has directed the agent to; no script is registered to run
automatically on page load.
```

---

## `tabs`

```
The agent works in tabs: it opens a page, switches between tabs, reads a tab's URL and title to
confirm it landed where it was asked to go, waits for a load to finish, and closes tabs it opened.
This permission is what lets it address a specific tab and know the state of the one it is in.
```

---

## `tabGroups`

```
Every agent session gets its own coloured, labelled Chrome tab group, and tabs the agent opens go
into it. This is a safety feature rather than a convenience one: without it the user cannot tell,
at a glance, which of the tabs in their window are theirs and which are the agent's. The
permission is used only to create a group and set its title and colour.
```

---

## `activeTab`

```
Used when the user starts an action from the extension's toolbar button: it grants access to the
tab they are looking at, at the moment they click, without the extension having to reach for
anything wider on its own initiative.
```

---

## `cookies`

```
Two user-driven tools need it. Reading cookies lets the agent confirm that a session is still
valid before it starts a task that will fail confusingly halfway through if it is not. Writing
cookies lets the user hand the agent a session they already have — for example moving a login into
a fresh profile — instead of typing credentials into a browser an agent is driving.

Both are treated as sensitive: the agent must ask for and receive the user's explicit approval at
the moment of the call before either can run. Cookie values are returned to the local process on
the user's own machine and are never sent anywhere else.
```

---

## `clipboardRead`

```
Pasting is often the only way in. Some editors, upload widgets and rich-text fields accept content
by paste and by nothing else, and copy-then-paste between two pages is frequently what the user is
actually asking the agent to do. Reading the clipboard is what lets the agent paste what is on it,
and lets it confirm a copy step actually succeeded before moving on.
```

---

## `clipboardWrite`

```
Lets the agent put text on the clipboard when the user asks it to copy something out of a page, or
when a paste-only target is the next step in the task.
```

---

## `storage`

```
Stores the extension's own connection state — whether the local server is reachable and on which
127.0.0.1 ports, which tabs belong to which agent session so those sessions survive a service
worker restart, and a rolling log of the last 50 actions (method name and timestamp) so the user
can open the popup and see what the agent did. That is all. No page content, no cookie or form
values, no credentials, and nothing about the user's own browsing is stored, and everything here
is removed when the extension is uninstalled.
```

---

## `offscreen`

```
The WebSocket to the local server has to stay open, and an MV3 service worker is terminated after
about 30 seconds of inactivity, which would drop the connection between commands. The extension
creates one offscreen document (reason: WORKERS) whose only job is to hold that connection to
127.0.0.1 and pass messages to the service worker. It has no UI, is never visible, and does
nothing else.
```

---

## `alarms`

```
A one-minute alarm checks that the offscreen document holding the local WebSocket is still alive
and recreates it if Chrome has torn it down. This is the standard MV3 keepalive pattern and is the
reason a session that has been idle for an hour still responds to the next command instead of
silently failing.
```

---

## `notifications`

```
When the agent needs a decision from the user — a choice it should not make for them, or a CAPTCHA
it could not clear and is handing back — it stops and waits. A Chrome notification is what tells
the user that, since the browser is usually in the background at that moment and an overlay in a
tab nobody is looking at is not a prompt. Notifications are raised only by that
waiting-on-the-user path; there are no marketing, promotional or engagement notifications.
```

---

## `webNavigation`

```
Used to enumerate the frames in a tab (webNavigation.getAllFrames) so the agent can act inside an
iframe — payment forms, embedded editors and admin widgets are routinely in one, and an action
aimed at the top frame simply misses. Used for frame discovery on the tab being acted on; not used
to observe the user's own navigation.
```

---

## Remote code

```
No. The extension executes no remote code. All logic is contained in the uploaded package; nothing
is fetched and evaluated from a server. The extension's content security policy permits connections
only to 127.0.0.1 (see content_security_policy in the manifest), and script-src is 'self'.

Script that the extension evaluates in a page is generated locally from the user's own instruction
via the local MCP server on their machine — it is user input, not code downloaded from a remote
host.
```

## If the reviewer pushes back

Two answers cover almost everything, and both are true:

1. **"Why does this need `debugger`?"** — trusted input events. Nothing else in the extension API
   surface can produce them, and without them the extension cannot fill in a form on a modern web
   app, which is its single purpose. See the block above; keep the CDP command list in the reply,
   it is the part that reads as an engineer rather than as marketing.
2. **"Where does the data go?"** — nowhere. One WebSocket, to `127.0.0.1`, on the user's own
   machine, refused unless it comes from this extension. The repository is public; invite them to
   check.

If a reviewer asks about CAPTCHAs, answer accurately rather than defensively: the tool detects the
common challenge types, attempts the checkbox, can pass an image grid to the agent's vision, and
falls back to handing the browser to the user — which is what happens most of the time. Do not
overstate the success rate, and do not deny the capability: the source is public and contradicting
it is worse than describing it plainly.
